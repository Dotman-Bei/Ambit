## How it was checked

A returned string is not proof. The signature was verified independently with `viem`:

```
signature bytes : 65  (r32 + s32 + v1)
EIP-191 digest  : 0x46fa3ec7962ac52eef7042e0424caa69b3aab5d79e2f0902fc1f79901ef8705f
recovered       : 0x14F4B95Ba8fC265C49D2cA16FB8673DA578eCF51
claimed wallet  : 0x14f4b95ba8fc265c49d2ca16fb8673da578ecf51
MATCH
```

The recovered address equals the wallet address, so the signature was produced by the private key
behind that wallet — reached through the delegated share, by the Ambit authority service.

## What this proves

- The delegated credentials are **usable**, not merely decryptable. Decryption proves the envelope
  opened; only a recovering signature proves the share works.
- `createDelegatedEvmWalletClient` and `delegatedSignMessage` operate against a live Dynamic
  environment. R1 and R2 are satisfied by execution, not by typechecking.
- The wallet is the end user's: the recovered address is the address Dynamic created at sign-in.

## What this does not prove

- **No money moved.** `delegatedSignMessage` signs a string; it authorises no transfer. G4 and R3
  remain unproven and require an x402 facilitator and funded Base Sepolia USDC.
- One wallet, one signature, one moment. It is not a claim about reliability.
- The message is self-describing and carries its instant, so this signature cannot be replayed as
  anything meaningful.

## Reproducing it

Console → Wallet → **Sign a test message**, with a delegation granted. The route is
`POST /delegation/probe`; it opens the stored credentials, signs, and returns the signature. The
key share is never included in the response.
